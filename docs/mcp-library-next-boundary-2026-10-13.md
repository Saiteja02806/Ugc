# Remaining Library and Explore slideshow MCP boundary

Read-only follow-up against current application source on 13 October 2026. The new eleven-tool Creative Asset group candidate is distinct from the application's saved Carousel/Slideshow Library. It does not complete full Library access.

## Existing services that the next adapters must share

`lib/library/db.ts` already provides `listLibraryCarouselItems`, `getLibraryCarouselItemForUser`, `removeLibraryCarouselItem` and `saveGeneratedCarouselToLibrary`. `/api/library` currently lists only carousel-type Library content. The save route resolves the owned generation, verifies ready rendered slide output and uses `loadSavedTrendingCreativeEditForDownstream` so edited content can be saved. An MCP adapter must preserve those downstream edit/output checks; calling the save RPC with fabricated slides is not equivalent to the application flow.

Library item identities and their saved slide rows are separate from generic visual `media_assets` IDs. `list_assets` and Creative Asset group membership therefore cannot stand in for Library list/detail/removal/save. A Library removal is a metadata change through its existing owner service and must not delete source media or become an unrestricted storage operation. Saved snapshots, edited versions and publishing dependencies must remain explicit.

Further SQL inspection changes the next write design: `save_generated_carousel_library_item` reuses an existing active owner/source Library item by replacing its saved metadata and slide rows. A replay of older inputs could therefore overwrite a newer saved edit if MCP merely calls that RPC again. The next save adapter needs a durable owner/request receipt and source/edit/output revision binding around that shared transaction. Receipts must recover an already accepted result without executing another replacement, and removed items must not be silently recreated. The separate `explore_save_slideshow` RPC already binds owner/request/fingerprint and rejects a deleted or mismatching existing save; keep these two save semantics distinct.

`lib/explore/slideshow-api.ts` already implements backend Library saves through the existing `explore_save_slideshow` transaction and a stable request key/fingerprint. Version 1 supports a checked catalogue reference; version 2 supports an ordered sequence of ready owned images, including a null catalogue reference. It validates 2–10 slides, owned/type/ready identities and trusted publishing URLs, preserves legacy request fingerprints and reports unconfirmed acknowledgements without minting another request. This existing save behavior should be extracted into an owner-aware shared service for MCP rather than forwarded an MCP token through Firebase HTTP.

## Rendering is still a separate missing backend workflow

The Explore slideshow's text export in `lib/explore/slideshow-text-client.ts` still loads an image, constructs its SVG text overlay, composites it through browser canvas and returns a PNG `File`. Backend Library save accepts the already rendered chosen images; it does not perform this text rendering. Adding only a save adapter would leave the user's requirement to create a finished text-bearing slideshow from an IDE incomplete.

The next rendering implementation must preserve existing slide design bounds, typography/crop behavior and exact authored text, resolve only owned/known reference media, render on a backend/worker, persist ordered output identities and support durable request/revision recovery before Library saving or publishing. Existing Trending Carousel rendering is a different contract and cannot be relabeled as Explore rendering without reviewing that shared behavior. `CAROUSEL_CONTEXT.md` remains the required source of truth before any such change; no Carousel architecture decision or code was changed in this audit.
