# Reaction-format context

Last updated: 2026-09-07

## Product definition

Reaction format is a separate Trending format. It is not a Carousel, a
Wall-of-text creative, or an existing full-frame Hook video.

Each 9:16 deliverable has three visual layers:

1. a reviewed static background image;
2. a reviewed transparent reaction clip; and
3. a short, AI-generated meme caption.

The output renderer always produces a normal H.264 MP4. Source ProRes 4444
clips are render inputs, not browser-preview assets.

## Source readiness decision

The supplied library was inspected on 2026-09-05.

- 61 MOV clips were found.
- All 61 are ProRes with an alpha-capable `yuva444p10le` video stream.
- 20 portrait background files were found; one is an exact duplicate, leaving
  19 unique catalog candidates. All can cover a 1080×1920 output.
- Source clips include portrait, square, and landscape framing. All are
  technically compositable, but each approved clip needs a reviewed
  foreground placement (anchor and height) before activation.
- The raw source library is roughly 1.4 GiB; it must remain server-side and is
  never sent directly to a browser.

Review sheets and a non-destructive manifest template are generated by:

```text
node scripts/inspect-reaction-assets.mjs
```

The generator does not activate assets. It places all new files in
`artifacts/reaction-asset-review/`, which is ignored by Git.

The generated manifest includes the exact controlled clip values and placement
options. The approved 61 clips and 19 backgrounds were marked `active` on
2026-09-06 and the manifest passes `--require-active` validation. Import still
requires the original local source files to be mounted, because their checksums
are deliberately verified before any upload.

## Phase 2: reviewed catalog import

The Phase 2 importer reads only `active` manifest entries. Before it creates
an active database row, it proves the current local file still matches the
reviewed checksum, uploads it to the Reaction storage namespace, and verifies
the uploaded object's size, content type, and checksum. It is safe to rerun:
an existing matching row/object is verified and skipped, while an object left
behind after a database failure is recovered on the next run.

Run a local, no-write plan after reviewing and activating at least one clip and
one background:

```text
node --experimental-strip-types scripts/import-reaction-assets.mjs --manifest <reviewed-manifest.json>
```

The actual remote import requires both `--execute` and `--yes`; `--verify`
performs a read-only database and storage integrity check afterwards.

## Phase 3: brief planning and batch selection

Phase 3 never lets AI choose a filename, clip ID, background ID, URL, or
storage key. It provides AI only with an internal reaction-intent palette
(fresh and reusable counts) and business context. AI returns short,
structured briefs with one to three reaction intents in priority order.

`planReactionBatch` is the application boundary for this flow. A generation
provider is injected into it, so its raw JSON is validated before any catalog
selection takes place. This keeps the eventual worker/provider integration
replaceable and prevents provider output from becoming a source of truth.

The application validates the response, then matches all requested briefs as
one batch against active assets. It chooses unique fresh clips first. If fresh
clips are insufficient, it may use distinct eligible clips previously shown to
that user, preferring lower use counts and longer-unseen clips. It never
duplicates a clip in the same batch merely to meet a requested count; a real
catalog shortfall is returned with unused-reaction hints for regeneration or
coverage work.

After review, validate the completed manifest with:

```text
node scripts/validate-reaction-asset-manifest.mjs --manifest <reviewed-manifest.json>
```

## Generated content dimensions

Each reaction creative must store these independently:

| Dimension | Values for V1 |
| --- | --- |
| Meme structure | Situation → payoff; expectation → reality; comparison; action → realization; setup → escalation |
| Language format | POV; when; me when; me after; me realizing; direct statement; comparison |
| Emotional payoff | Relief; frustration; surprise; regret; satisfaction; irony; escalation |
| Visual treatment | White card; outlined text |

These belong to the generated creative, not the asset catalog. The caption
stores semantic beats in addition to its rendered lines. This lets analytics
identify whether the structure, wording wrapper, emotion, or visual treatment
produced the result.

## Asset metadata and gating

No reaction clip may enter matching until it has all of:

- `status = active`;
- confirmed alpha;
- one to three visible reactions, in priority order;
- subject count;
- composition; and
- foreground placement (anchor and height percentage).

No background may enter matching until it has all of:

- `status = active`;
- one or more soft context tags; and
- one foreground placement.

Technical metadata is machine-derived and is not a review tag: source root,
filename/checksum, dimensions, duration, codec, pixel format, alpha result,
and renderable storage key. The database blocks an `active` asset without a
storage key, so matching cannot hand a worker an asset that it cannot fetch.

The matcher first rejects assets that fail this gate. It then scores the
emotion-to-reaction fit, context-tag affinity, placement compatibility, and
recent-use diversity. V1 deliberately omits character-label treatments: there
is no separate label renderer, so the worker produces only complete visual
treatments rather than persisting a non-rendered option.

## Copy policy

Reaction copy is concise: 5–20 words, one to three semantically balanced
lines, with a 7–15 word target. The generated caption must represent a
human moment, not feature copy or a CTA. Product claims such as “our AI
automatically…” are rejected before matching.

## Rendering rules

- Canvas: 1080×1920, 30 fps, H.264 MP4 output.
- Caption: upper safe band; white-card and outlined variants remain separate.
- Foreground: a per-asset anchor/scale is applied after the background has
  been cropped to the output canvas. Never infer this from source dimensions
  alone.
- V1 has no 30-day-plan behavior. A requested count creates that many
  independently matched reaction creatives.

## Legal and quality review

Several source clips visibly depict recognizable people, film/TV characters,
logos, and watermarks. Technical alpha suitability is not permission to
distribute them. A reviewer activates a source only after deciding it may be
used; this decision is represented by the single asset `status`, rather than
additional catalog tags.

## Phase 4: Trending delivery and scheduling

Reaction delivery uses the existing Trending daily-slot and decision system;
it does not introduce a second feed or a second scheduler.

- `reaction_creatives` holds the selected clip/background pair, generated
  content, render plan, and final media-asset reference. A record can enter
  Trending only when `render_status = preview_ready`, its final media asset
  exists, and it has an HTTPS preview URL.
- `user_reaction_assignments` is the per-user item that may be offered in a
  daily slot. `reaction_clip_presentations` records the first real appearance
  of that assignment, rather than treating generation or a slot reservation as
  a view.
- `daily_trending_feed_slots` binds a Reaction assignment just like Carousel,
  Hook, and Wall-of-text items. The shared swipe decision is immutable: left
  records `rejected`; right records `accepted`. A scheduler request repeats
  the idempotent accepted decision before using the media, protecting a very
  fast swipe from a delayed browser outbox.
- The Reaction card is the same 9:16 review frame used by Hook and Wall-of-
  text. It plays the final MP4 only; the browser never composites alpha video,
  background, or caption layers.
- A right swipe opens the existing `PlatformSelectionModal` directly. It
  schedules the final owner-scoped `reaction_render` media asset through the
  normal media-asset path. The schedule idempotency key is derived from the
  assignment, so retries cannot create a duplicate post.
- The default mix is 20% Slideshows, 30% Wall-of-Text, 20% Reaction Reels,
  and 30% Hooks: Free receives 2/3/2/3, Starter 4/6/4/6, and Growth
  10/15/10/15 per day. The Adjust dialog exposes all four percentages and
  redistributes the remaining share proportionally when one is changed.
  A Reaction slot is attached only to a ready final creative or reported as
  unavailable; raw sources are never substituted.

`lib/reaction-format/` remains the shared boundary for catalog validation,
AI brief validation, batch matching, and render-plan rules. These rules must
not be folded into Wall-of-text or Hook-video validation.

## Phase 5: durable generation and rendering

The durable worker starts from a `reaction_generation` background job. It
creates one `reaction_generation_runs` record and saves the validated brief,
chosen clip/background pairs, creative records, and user assignments in
`reaction_generation_run_items` before rendering any video. A retry or
reclaimed job reads that saved plan; it does not ask AI again or pick different
assets.

For each pending item the worker privately reads the catalog background and
alpha clip from storage, renders the 1080×1920 captioned composition into an
H.264 MP4, creates the owner-scoped `reaction_render` media asset, and marks
the creative `preview_ready`. A failed item stays durable and is retried on
the next worker attempt; items that already rendered are skipped. Trending
only sees those final ready MP4s.

The durable worker uses the same five semantic-beat shapes as the shared
Reaction content contract: situation/payoff, expectation/reality, left/right,
action/realization, or setup/escalation. It also rejects product-selling copy
before a brief can be persisted. This prevents the worker from creating a
different content shape than the planner validates.

Active assignments with a queued, rendering, or preview-ready creative reserve
their clips. The planner excludes those reserved clips, and the database
serializes per-user/profile planning and enforces the same rule at persistence
time. A terminally failed render is not a permanent reservation. A five-slot
request may therefore finish with only three unique eligible Reels. That is a successful partial
result—not a duplicate refill: Trending keeps the three ready items and marks
the two unresolved slots with an explicit approved-catalog-coverage message.
If no item reaches preview-ready state, the worker marks both the durable run
and its background job failed so the normal recovery/retry behavior applies.
An individual clip is eligible for at most two real presentations to the same
user (the first appearance and one later reuse); catalog reservation does not
count as a presentation.

## Reaction brief latency and repair — 7 September

The worker's `reaction-brief-batch-v2` provider response omits `caption`.
Rendered `lines` remain canonical; the worker derives and persists the same
caption field that existing consumers use. Semantic beats and the other
content dimensions remain intact. The prompt supplies the validator's exact
emotion/primary-reaction compatibility matrix and distinct-primary rule.
Catalog intents unsupported by every V1 emotion are excluded before asking AI.

The default GPT-5 Mini request uses `minimal` reasoning, a 60-second timeout,
and no SDK retries. Explicit model overrides outside the GPT-5 Mini alias or
dated snapshot retain the existing `low` reasoning setting. The reduced
reasoning setting does not bypass deterministic copy or catalog validation.

Within the existing three-request validation budget, accepted briefs are
retained and only missing or invalid slot indexes are requested again.
Duplicate primary reactions or slot indexes cannot replace an accepted
sibling. The final combined batch passes the full existing validator before
matching or persistence. A provider outage still yields to durable retry;
these in-memory accepted briefs are not a new durable partial-plan checkpoint.
Exhausting the validation budget still fails explicitly instead of delivering
invalid content.

Worker logs record the job ID, model, reasoning setting, requested slots,
request duration, token usage, validation repair slots, and matching duration.
They omit business context, generated captions, and credentials. Persisted
plans remain immutable and are reused on render retries as before.
